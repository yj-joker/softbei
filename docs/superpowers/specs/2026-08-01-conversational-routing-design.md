## 1. 背景与问题

当前系统已有意图路由、设备范围判定、证据资格、回答审计和图片筛选，但这些状态没有形成统一的下游回答契约。最近一次 130 case / 134 turn 测评结果为：最终通过率 54.62%、范围隔离 30%、无答案克制率 38.89%、多轮通过率 0%、图片通过率 75.76%、步骤顺序 100%。

已观察到的问题包括：

1. 通用问题（高等数学、身份、模型信息）被错误送入设备知识检索。
2. 明确询问飞机时引用摩托车手册，跨设备证据泄漏。
3. “右曲轴箱盖”被回答成“左曲轴箱盖”，并且文本提及图示时没有返回对应图片。
4. 无设备文档与明确文档冲突都被粗略处理为同一类 `out_of_scope`。
5. 统一审计和确定性兜底使回答模板高度重复，同时不能满足“无对应文档时由 AI 参考回答”的产品设计。

## 2. 目标与非目标

### 2.1 目标

1. 保留现有意图识别，不增加第二套意图分类器。
2. 由意图、范围、证据覆盖和风险等级派生统一 `response_policy`。
3. 通用问题直接使用模型能力，不触发设备知识检索。
4. 设备无对应文档时允许 AI 通用回答，但必须披露来源并禁止伪装成手册结论。
5. 明确设备或手册冲突时阻断错误手册引用。
6. 对设备、部件、方向、动作、参数、步骤和图片建立一致性门禁。
7. 将事实和安全要求固定，将非关键语言表达改为受控随机。
8. 规则只能在适用设备和审核状态匹配时生效，并可追溯到来源和测评用例。

### 2.2 非目标

1. 不重做现有意图枚举、向量模型、知识导入或知识图谱。
2. 不允许提高全局随机性来替代事实约束。
3. 不把模型生成的回答自动发布为正式领域规则。
4. 不改变外部 Java API 协议；新增诊断信息继续放入已有 `metadata`。
5. 不覆盖或回滚工作树中本轮之前的用户改动。

## 3. 核心设计

### 3.1 意图与回答契约分离

`intent_decision` 只描述用户想做什么；`response_policy` 描述当前资料和范围条件下允许如何回答。它是已有状态的派生对象，不触发二次 LLM 分类。

建议模式：

- `GENERAL_AI`：闲聊、身份、通用知识、模型信息。
- `GROUNDED_KNOWLEDGE`：设备文档和问题证据完整匹配。
- `PARTIAL_GROUNDED`：部分要点有证据，逐项披露缺失内容。
- `MAINTENANCE_AI_FALLBACK`：没有设备文档，或低中风险问题没有对应主题证据。
- `INSUFFICIENT_EVIDENCE`：精确参数或高风险操作没有可靠依据。
- `BLOCKED_SCOPE`：用户明确指定的设备或手册冲突。
- `EVIDENCE_CONFLICT`：同一设备的证据发生不可消解冲突。

`response_policy` 至少包含：`mode`、`intent`、`knowledge_status`、`scope_status`、`source_type`、`risk_level`、`disclaimer_required`、`manual_citation_allowed`、`images_allowed`、`ai_fallback_allowed`、`required_facts` 和 `style_profile`。

### 3.2 路由顺序

1. 先识别身份、通用知识和社交闲聊；这些请求不进入检索范围门禁。
2. 对检修请求提取设备、部件、左右方向、动作、请求要点和风险等级。
3. 显式设备或手册冲突进入 `BLOCKED_SCOPE`。
4. 识别出设备但没有对应资料时清空旧设备检索范围，进入 `MAINTENANCE_AI_FALLBACK`。
5. 只有设备、文档、主题和实体都匹配时，才进入手册证据回答。

范围状态需要区分：`IN_SCOPE`、`NO_MATCHING_DEVICE_DOCUMENT`、`EXPLICIT_DOCUMENT_CONFLICT`、`UNKNOWN_SCOPE` 和 `DOCUMENT_NOT_FOUND`。未指定新设备时可继承已确认会话范围；用户明确切换设备时必须重置旧范围。

### 3.3 回答和来源规则

- `GENERAL_AI`：不显示“知识库没有手册”，不引用设备手册。
- `MAINTENANCE_AI_FALLBACK`：明确说明知识库没有对应设备资料、回答来自 AI、仅供参考；不得生成无依据的精确参数或伪装成手册步骤。
- `GROUNDED_KNOWLEDGE`：只能使用合格证据，显示真实页码和来源。
- `BLOCKED_SCOPE`：只说明冲突并要求切换或上传资料，不生成具体维修结论。
- `INSUFFICIENT_EVIDENCE`：说明资料未覆盖，提供安全边界或补充资料要求，不编造数值和高风险步骤。

### 3.4 实体和回答范围门禁

检索和最终审计均检查设备、部件、方向、动作、章节和问题要点。`左/右`、`安装/拆卸`、`连接/断开` 等相反词属于硬冲突；证据或回答命中相反实体时不得通过。

回答计划只允许覆盖用户请求的要点，禁止将一个局部问题扩展成完整相邻章节。对于“如何安装右曲轴箱盖”，目标章节应为 `6.4 右曲轴箱盖与离合器/安装右盖`，重点页为 26、27，不得使用左盖章节。

### 3.5 图片契约

手册图片必须绑定到最终使用的证据章节、页码、方向和动作。`GENERAL_AI`、`MAINTENANCE_AI_FALLBACK` 和 `BLOCKED_SCOPE` 不返回手册图片。文本出现“如图所示”时必须存在匹配 `evidence_images`；否则删除该表述或改为文字说明。流式和非流式接口使用同一个最终图片筛选器。

## 4. 受控随机性

事实、安全要求、来源、方向、参数、页码和步骤顺序保持确定；开头、段落组织、过渡语和通用例子允许变化。按回答类型设置不同随机性：通用知识 0.7-0.9、AI 检修兜底 0.5-0.7、手册说明 0.2-0.4、参数和步骤 0.1-0.3、范围阻断 0.1-0.2。

通过 `session_id + turn_id` 或审核过的表达变体选择风格，避免同会话漂移和测评不稳定。测评比较事实、禁答项、来源、方向、步骤、图片和必要提示，不比较整段文字完全相同。

## 5. 规则沉淀治理

领域规则需要有 `rule_id`、版本、状态、适用设备、文档版本、部件、动作、条件、结论、安全等级、证据来源、审核人和关联测评用例。生命周期为：候选规则 -> 绑定证据 -> 人工审核 -> 专项回归 -> `active` -> 冲突检测 -> `deprecated/superseded`。

规则优先级为：范围门禁 > 同设备手册证据 > 同设备已审核规则 > 同设备图谱 > AI 通用能力。任何规则不得跨设备复用；模型回答不能直接变成正式规则。

## 6. 测评与验收

新增覆盖通用知识、身份、模型信息、无设备文档、明确冲突、左右件反向、部分证据、证据冲突、回答聚焦、图片一致性、多轮范围切换、规则版本和表达多样性。

第一阶段硬门禁：通用问题误检索率 0、跨设备引用率 0、明确冲突阻断率 100%、无文档提示覆盖率 100%、关键左右件错误率 0、参数/方向/步骤多次生成一致率 100%、现有步骤顺序通过率保持 100%。质量目标为范围隔离至少 95%、无答案克制至少 90%、多轮至少 90%、图片至少 90%、回答-证据对齐至少 95%、最终通过率先达到 80%。

## 7. 实施顺序

1. 先补通用路由、范围状态和 `response_policy` 的失败测试。
2. 实现路由和范围门禁，确保无设备文档不引用旧手册。
3. 实现实体一致性、回答聚焦和统一来源元数据。
4. 合并流式和非流式最终审计及图片契约。
5. 增加受控随机性和规则治理字段。
6. 扩充专项测评，运行局部测试、全量测评和回归比较器。

每个生产改动都必须先有失败测试并观察到红灯，再实现最小修改并验证绿灯。实施过程中只修改本方案涉及的文件，保留工作树既有改动。
