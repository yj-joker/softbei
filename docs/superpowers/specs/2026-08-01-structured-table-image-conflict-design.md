# 结构化表格、证据图片与冲突澄清优化设计

日期：2026-08-01
状态：已获用户确认，进入实施
目标分支：`feature/rag-quality-v2`

## 1. 问题范围

本轮解决三类已由完整测评暴露的问题：

1. 跨页表格被合并后，续页行失去真实页码；API 又从文本反解析表格，导致行列错位、精确字段遗漏和无关数字冲突。
2. 图片经过检索层和 API 多层筛选，且检索层固定最多两页，造成跨三页操作少图、单步骤问题多图、错页和文本/图片未绑定。
3. 系统已有根因追问和证据冲突提示，但分别是硬编码场景和无状态提示，下一轮不能统一恢复并继续回答。

## 2. 设计原则

- 结构化数据只解析一次：导入/分块阶段生成稳定元数据，下游读取结构化字段，不再依赖展示文本恢复语义。
- 最终证据决定图片：先确定回答使用的证据、步骤和页面，再选择覆盖这些要点的最小图片集合。
- 冲突只比较同一语义字段：序号、数量和规格中的普通数字不得被当作同一参数值互相冲突。
- 澄清可恢复：反问必须携带稳定 `clarification_id` 和待解决状态，下一轮可以恢复原证据并重新决策。
- 兼容旧索引：新索引写入新字段；读取端同时接受旧 `table_full`、旧图片元数据和旧 `diagnostic_follow_up`。

## 3. 结构化表格契约

### 3.1 表级元数据

每个 `table_full` chunk 写入：

```json
{
  "table_id": "sec-id:table:0000",
  "continuation_id": "sec-id:table:0000",
  "page_span": [17, 18],
  "headers": ["序号", "零件名称", "数量", "备注"],
  "rows": []
}
```

`page_span` 是有序去重的实际来源页，不使用字符串范围承担逻辑。`continuation_id` 用于表示跨页续表属于同一逻辑表；非跨页表与 `table_id` 相同。

### 3.2 行级元数据

每一行写入：

```json
{
  "row_id": "sec-id:table:0000:row:0012",
  "source_page": 18,
  "source_index": 12,
  "fields": {
    "序号": "13",
    "零件名称": "M10 盖形法兰面螺母",
    "数量": "4",
    "备注": "14# 套筒 / 60 ± 5 N·m"
  }
}
```

`table_row` chunk 的 `page` 必须等于该行 `source_page`。旧索引没有结构化行时，读取端保留原文本解析作为兼容分支。

### 3.3 精确查询与冲突

- 精确表格问题先匹配目标行，再投影用户请求字段，例如“数量”“扭矩”“规格”。
- 同一行的备注可派生扭矩，但必须保留原备注。
- 参数冲突键由规范化的语义字段、对象、单位组成；序号和数量仅在用户明确询问对应字段时参与资格判定，不参与通用扭矩/间隙等参数冲突。
- 跨页答案的来源页来自命中行；完整清单来源可显示 `page_span`。

## 4. 图片选择契约

新增统一的图片选择契约，内部模式为：

- `none`：用户明确不要图片，或回答策略禁止图片。
- `single_target`：只问一个步骤、部件位置或“哪一张图”。
- `evidence_pages`：回答使用多个步骤或跨页操作，图片覆盖全部证据页。
- `section_overview`：用户明确要求整节/全部相关图片。

契约至少包含：`mode`、`target_pages`、`target_evidence_ids`、`target_step_ids`、`document_id`、`section_id`、`action`、`orientation`、`explicit_pages` 和 `excluded_pages`。

选择流程只有一次最终裁决：

1. 从最终 `ResponsePlan.allowed_evidence` 提取实际回答页面、步骤和证据 ID。
2. 应用文档、章节、动作、左右方向、显式页和禁止页硬约束。
3. `single_target` 选择与目标步骤绑定置信度最高的一张；不自动添加相邻页。
4. `evidence_pages` 选择覆盖全部目标页面/步骤的最小集合，不设置固定两页上限。
5. 输出图片附带 `stepId`、`aspectId`、`page`、`role` 和 `bindingConfidence`，供 API 和前端审计。

旧索引只有 `related_step_chunk_ids` 时继续读取，但只作为低置信度候选；新索引按图片所在页和步骤来源页建立确定绑定。

## 5. 通用冲突澄清状态

统一状态 `PendingClarification`：

```json
{
  "clarification_id": "clarification-...",
  "kind": "evidence_conflict",
  "subject": "气缸头 M10 螺母锁紧扭矩",
  "alternatives": [],
  "evidence_refs": [],
  "missing_identity_fields": ["设备型号", "文档版本"],
  "question": "请确认设备型号或适用的手册版本。",
  "status": "awaiting_answer"
}
```

冲突分三类：

- 表面冲突：对象、动作、方向、型号或字段不同。自动分组解释，不反问。
- 真实冲突：同一对象和同一字段在相同适用范围出现不同值。生成可恢复反问。
- 信息不足：无法确定型号、版本或规则范围。询问最小必要身份字段。

下一轮通过 `clarification_id` 恢复原查询、候选证据与替代项；用户选择选项或补充型号/版本后重新过滤并生成回答。现有 `diagnostic_follow_up` 映射到同一公共状态结构，保留旧字段兼容。

## 6. 验收标准

- 12 条历史表格/精确字段失败用例全部通过。
- 66 条图片用例的召回、精确率、顺序和绑定全部通过；三页操作可返回三页，单步骤不返回相邻步骤页。
- 3 条历史冲突用例通过，并新增冲突第二轮恢复端到端测试。
- 步骤顺序继续保持 `31/31`。
- 在新代码和重建索引上完整运行 130 条测评，报告所有汇总指标、失败 case ID 和原因。
