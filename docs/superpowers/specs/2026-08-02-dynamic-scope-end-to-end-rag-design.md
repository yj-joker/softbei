# 动态设备范围与端到端 RAG 可靠性优化设计

日期：2026-08-02

状态：用户已确认
目标分支：`feature/rag-quality-v2`

## 1. 目标

本设计解决当前检修对话链路中已经复现的设备串库、意图错路由、证据覆盖误判、表格与图片重复、跨页来源丢失、多轮动作污染、冲突反问不可恢复、固定话术、流式终态卡死、运行版本不透明和规则沉淀范围不足问题。

核心目标如下：

1. 设备范围识别不得依赖人工登记未支持设备名称或关键词别名。
2. 只有查询设备与知识库动态目录明确匹配时才允许检索对应手册。
3. 闲聊和通用知识直接使用模型能力；缺少设备手册的检修问题使用带来源声明的安全 AI 通用兜底。
4. 表格、步骤、图片、页码和证据绑定必须从导入到最终输出保持结构化来源。
5. 最终用户可见答案只能由一个回答计划生成，审计失败不得退化为原始证据拼接。
6. 测评必须覆盖最终流式接口和用户可见答案，不能只验证局部函数。

## 2. 已确认问题

### 2.1 设备范围和路由

- “飞机发动机”和“卡车发动机”曾错误返回摩托车发动机手册。
- “飞机发动机”后来通过 `external_devices.aliases` 静态登记被识别，这仍属于配置化关键词写死，不能泛化到未登记设备。
- 高等数学、“你是谁”和模型身份问题错误进入知识库不足模板。
- 没有对应设备文档时，系统没有稳定利用模型通用能力回答。

### 2.2 检索、覆盖和最终审计

- 右曲轴箱盖曾命中左曲轴箱盖章节。
- 安装、拆卸和检查内容出现混杂。
- 完整表格已被检索和格式化，但覆盖状态仍为 `partial`。
- 确定性表格答案被 `unsolicited_manual_lead` 否决，回退为 `table_row + image_summary + table_full` 原始证据拼接。
- 完整答案末尾错误追加“当前资料没有明确说明”。
- 普通来源模式与“根据手册”开头互相冲突。

### 2.3 表格和图片

- 跨页表格存在 `page_range=17-18`，但最终来源只使用首个 `page=17`。
- 当前重建索引没有稳定保存 `page_span`、`table_full.rows[].source_page` 等结构化来源。
- 同一表格的行块、整表和图片摘要重复进入正文。
- 多图、少图、错页、禁图页和图片步骤绑定由多层独立筛选造成。
- 单步骤问题可能返回相邻步骤图片，跨页操作又可能被固定页数上限截断。

### 2.4 多轮、冲突和运行闭环

- 当前轮“安装离合器”“拆卸离合器”会继承上一轮右曲轴箱盖内容或相反动作。
- 冲突测评没有稳定注入两份独立合格证据，导致冲突处理统计为 0。
- 冲突反问和根因追问没有统一、可持久化的恢复状态。
- Python、Java 和前端对 SSE `done/error` 终态处理不一致，出现“正在校验证据”卡死。
- 运行服务缺少源码、工作树、文档和索引版本握手，测评代码与实际服务版本可能不一致。

### 2.5 回答风格和规则沉淀

- AI 兜底过度依赖固定模板，措辞和结构重复。
- Emoji 约束依赖末端清洗，而不是统一上游风格契约。
- 沉淀规则缺少完整的设备、型号、版本、部件、动作和来源适用范围。

## 3. 不采用的方案

### 3.1 扩充静态设备别名

不采用。它只能处理已经预见的设备名称，不能证明对未知设备的范围隔离能力。

### 3.2 纯大模型路由

不采用为唯一裁决者。纯模型判断具有泛化能力，但可能因为“发动机”等共性词把不同设备误判为同一范围。

## 4. 推荐架构

采用“结构化查询契约 + 动态知识目录 + 三态范围裁决 + 单一回答计划”。

处理顺序固定为：

1. 从当前问题生成 `QueryContract`。
2. `ScopeResolver` 将查询设备身份与知识库动态目录比较。
3. 根据意图、范围、风险和证据派生唯一 `ResponsePolicy`。
4. 仅在范围明确匹配时执行限定文档检索。
5. 基于原始用户问题建立不可变必答点。
6. 生成结构化 `AnswerArtifact`。
7. 执行一次证据、来源、图片和风格终审。
8. 通过统一 SSE 终态协议发送结果。

## 5. QueryContract

`QueryContract` 是当前轮唯一语义输入，至少包含：

```json
{
  "intent": "maintenance_guidance",
  "raw_device_span": "卡车发动机",
  "device_category": "发动机",
  "carrier_or_application": "卡车",
  "manufacturer": "",
  "model": "",
  "component": "",
  "action": "fault_diagnosis",
  "orientation": "",
  "risk_level": "medium",
  "source_request": "normal",
  "answer_aspects": []
}
```

约束：

- `raw_device_span` 必须能回指原始问题中的连续文本，防止模型编造设备。
- 当前轮显式设备、部件、动作和方向必须覆盖历史值。
- 检索扩展词不得写入 `answer_aspects`。
- 抽取使用结构化输出、低温度、模式校验和一次受控重试。

## 6. 动态知识目录与无关键词范围裁决

### 6.1 动态目录来源

每次文档导入时，从封面、标题、文档元数据和用户提供的设备信息生成 `DocumentIdentity`：

```json
{
  "document_id": "...",
  "device_name": "摩托车发动机",
  "device_category": "发动机",
  "carrier_or_application": "摩托车",
  "manufacturer": "",
  "model": "",
  "manual_type": "维修手册",
  "document_version": "v1",
  "index_revision": 3
}
```

该身份写入文档 manifest，并传播到所有文本、表格和图片块。生产配置不再维护未支持设备的 `external_devices` 列表。

### 6.2 三态范围裁决

`ScopeResolver` 只返回：

- `matched`：查询设备与目录条目明确一致，可以检索对应文档。
- `unmatched`：存在载体、制造商、型号或应用范围冲突，禁止知识库检索。
- `uncertain`：信息不足，进入最小反问或安全通用兜底。

候选相似度只用于缩小目录候选，不能直接授权检索。最终必须由受约束的同一性判断确认没有冲突属性。无法确认时采用保守策略，宁可不引用手册，也不能引用错误设备手册。

### 6.3 范围优先级

1. 前端明确选择的设备或文档。
2. 当前问题明确出现的设备身份。
3. 当前会话已经确认的设备绑定。
4. 唯一高置信度章节候选；高风险问题仍需确认设备。
5. 无法确认时不得退回全库检索。

## 7. 回答策略

不增加第二个回答模式分类器。`ResponsePolicy` 由意图、范围、风险和证据确定性派生：

- 闲聊、通用知识、模型身份：模型原生回答，不检索，不添加设备手册提示。
- 检修且范围匹配：限定文档检索并生成有证据回答。
- 检修但范围不匹配：AI 通用兜底，禁止引用当前手册和返回其图片。
- 范围不确定：低中风险可以给通用方向并说明设备未确认；高风险或精确参数询问最小必要身份。
- 缺少证据的高风险操作：可以给安全准备和停止条件，不得生成设备专用参数和完整拆装步骤。

AI 通用兜底必须表达三个语义，但不固定句式：

1. 当前知识库没有该设备对应文档。
2. 内容由 AI 基于通用知识生成。
3. 内容仅供参考。

## 8. 证据覆盖与 AnswerArtifact

### 8.1 不可变必答点

必答点只从原始问题生成。设备身份是范围约束，不应自动成为一个待回答内容；检索查询扩展也不能制造用户可见的缺失项。

证据支持按完整章节、逻辑表格和步骤集合聚合判断，不能要求整个问题字符串被某个单独 chunk 包含。

### 8.2 单一最终对象

所有入口统一输出：

```json
{
  "content": "...",
  "coverage": "complete",
  "evidence_refs": [],
  "source_pages": [],
  "images": [],
  "scope_decision": {},
  "response_policy": {},
  "audit": {}
}
```

最终审计不得把已经通过证据校验的确定性表格或步骤答案替换成原始证据拼接。风格违规只能修复措辞，不能改变事实、覆盖状态或证据集合。

普通、原文和页码来源模式只控制引用形式，不能决定一个有证据答案是否合法。

## 9. 表格契约

导入阶段生成：

- `table_id`
- `continuation_id`
- `page_span`
- `headers`
- `rows[].row_id`
- `rows[].source_page`
- `rows[].source_index`
- `rows[].fields`

回答规则：

- 完整清单只使用一个结构化 `table_full` 渲染。
- `table_row` 只用于召回和定位，不能重复进入正文。
- 图片摘要不能进入表格正文。
- 精确字段问题只投影目标行和用户请求字段。
- 完整清单来源使用 `page_span`；精确行问题使用命中行来源页。
- 原表重复序号不擅自修正，必要时注明“原表序号如此”。

## 10. 图片选择契约

图片只在最终证据确定后进行一次选择。每张图片必须携带：

- `document_id`
- `section_id`
- `source_page`
- `action`
- `orientation`
- `step_ids`
- `evidence_ids`
- `binding_confidence`

选择规则：

- 单部件或单步骤只返回目标图片，不自动扩展相邻页。
- 多步骤跨页操作选择覆盖实际回答步骤的最小图片集合，不设置固定两页上限。
- 左右方向、安装拆卸动作和显式禁图页作为硬约束。
- 图片说明和图片资源分离，说明不得重复进入正文。
- 图片数量、顺序和步骤绑定由同一个选择契约产生，API 和前端不得再次改变语义选择。

## 11. 多轮和冲突澄清

多轮状态只保存结构化槽位：设备、文档、部件、动作、方向、版本、证据引用和待澄清状态。

当前轮显式字段永远覆盖历史。只有当前轮省略的字段才允许继承，避免安装、拆卸、检查和相邻部件互相污染。

真实冲突必须满足同设备、同适用版本、同部件、同动作、同参数和同单位，不同值才进入反问。序号、数量和不同字段的普通数字不得触发冲突。

统一 `PendingClarification` 保存：

- `clarification_id`
- `kind`
- `original_query`
- `alternatives`
- `evidence_refs`
- `missing_identity_fields`
- `status`

下一轮根据选项、页码、型号或版本恢复原证据继续回答。

## 12. 风格与 Emoji

- 有证据参数、表格和步骤使用低温度，保证事实和顺序稳定。
- 闲聊和 AI 通用兜底使用适度温度，避免固定开头和固定结构。
- 提供最近回答结构用于避免连续重复措辞。
- 免责声明采用语义审计，不校验固定字符串。
- 从提示、示例和风格配置中删除 Emoji 生成要求和示例。
- Emoji 违规时重新生成一次；末端清洗不作为主要控制机制。

## 13. 规则沉淀

沉淀规则采用结构化适用范围：设备身份、型号、版本、部件、动作、症状、条件、结论、证据来源、置信度和状态。

生命周期为：

```text
用户反馈 → 候选规则 → 证据校验 → 回归测评 → 审核启用 → 版本化 → 失效或回滚
```

候选规则不得立即覆盖手册。规则必须在设备范围裁决之后匹配；与手册发生真实冲突时进入统一澄清，不静默选择。文档重导入后自动重新验证受影响规则。

## 14. 流式终态、重导入和版本握手

- Python 每次请求只能发送一个终态：`done` 或 `error`。
- 校验期间可以发送状态事件，但不能提前结束流。
- 超时返回最后一个已验证答案或安全兜底，并发送终态。
- Java 以终态事件为持久化完成依据。
- 前端收到终态后清理加载状态，重复终态通过事件 ID 幂等处理。
- 文档重导入递增 `index_revision`，使范围目录、章节目录和检索缓存失效。
- 健康检查暴露 Git commit、工作树标识、Python/Java 版本、文档 ID 和索引版本。
- Java 与 Python 建立版本握手，防止最新前端连接旧服务。

## 15. 验收标准

### 15.1 针对性真实问题

- 飞机、卡车以及代码和配置中未出现过的设备问题：使用 AI 通用兜底，摩托车手册引用和图片均为 0。
- 高等数学、“你是谁”和模型身份：模型原生回答，无设备手册提示。
- 右曲轴箱盖安装：只命中右盖第 26–27 页及绑定图片，不出现左盖。
- 安装离合器、拆卸离合器：动作和对象隔离，不携带上一轮无关步骤。
- 气缸活塞清单：每行一次、无图片摘要正文、无矛盾缺失提示、来源第 17–18 页、覆盖完整、审计通过。

### 15.2 指标门槛

- 步骤顺序保持 `31/31`。
- 图片专项至少 `25/30`。
- 未支持设备错误引用率为 0。
- 完整证据回答矛盾缺失提示为 0。
- 冲突现有 3 例达到 `3/3`，并通过第二轮恢复测试。
- SSE 终态到达率 100%。
- 流式和非流式最终正文、覆盖状态、来源和图片一致。

### 15.3 测评可信度

- 范围隔离测评不得预注入 `device_type` 或 `document_id`。
- 使用未出现在生产代码、配置和提示词中的设备作为留出集。
- 必须断言最终用户可见正文，而不是只断言局部函数输出。
- 每次测评记录代码版本、工作树、文档版本和索引版本。
- 报告全部失败 case ID、最终正文、证据页、图片列表和失败原因。

## 16. 实施边界和顺序

1. 先增加端到端失败测试和运行版本记录。
2. 实现 `QueryContract`、动态目录和三态范围裁决，删除静态外部设备别名。
3. 统一 `ResponsePolicy`、证据覆盖和最终回答审计。
4. 修复结构化表格、跨页来源和唯一渲染。
5. 合并图片选择并重建步骤绑定。
6. 修复多轮槽位和冲突恢复。
7. 接入规则沉淀范围、版本和上线门禁。
8. 修复 SSE 终态和版本握手。
9. 重建索引，运行针对性用例和完整测评。

本设计不包含无关 UI 重构，不改变已经验证正确的步骤原文顺序，也不通过新增未支持设备关键词实现范围隔离。
